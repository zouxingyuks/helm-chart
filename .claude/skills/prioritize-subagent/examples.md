# Prioritize Subagent - 使用场景示例

本文档提供真实的使用场景示例,展示���时使用 subagent vs 何时直接使用工具。

## 场景 1: 理解认证系统

### ❌ 不推荐的做法

```
用户: "解释一下这个项目是如何处理认证的"

助手: 直接使用 Grep 工具搜索 "auth" 关键词
```

**问题:**
- 可能找到不相关的结果 (如 "author", "authenticate" 等)
- 无法理解认证流程的整体架构
- 需要手动综合多个文件的信息
- 可能遗漏关键的认证组件

### ✅ 推荐的做法

```
用户: "解释一下这个项目是如何处理认证的"

助手: 使用 Explore subagent (medium thoroughness)
"找到并理解项目中用户认证系统的实现,包括认证流程、Token 管理、
会话处理等关键组件。返回每个组件的文件路径、功能说明和相互关系。"
```

**优势:**
- 能够理解认证系统的整体架构
- 自动找到所有相关组件 (中间件、模型、控制器等)
- 提供清晰的流程说明
- 识别不同的认证策略 (JWT、Session、OAuth 等)

**预期输出:**
```
项目使用 JWT 认证系统,主要组件包括:

1. src/auth/middleware/jwt.ts - JWT 验证中间件
   - 验证请求头中的 Token
   - 解析用户信息并附加到请求上下文

2. src/auth/services/token.service.ts - Token 管理
   - 生成访问 Token 和刷新 Token
   - 处理 Token 续期和撤销

3. src/auth/controllers/auth.controller.ts - 认证控制器
   - POST /auth/login - 用户登录
   - POST /auth/refresh - 刷新 Token
   - POST /auth/logout - 用户登出

4. src/auth/strategies/jwt.strategy.ts - JWT 策略
   - 验证 Token 有效性
   - 从 Token 中提取用户信息

认证流程:
1. 用户通过 /auth/login 提交凭据
2. 验证成功后生成 JWT Token
3. 客户端在后续请求中携带 Token
4. 中间件验证 Token 并授权访问
```

## 场景 2: 修复特定 Bug

### ❌ 不推荐的做法

```
用户: "登录时出现 500 错误"

助手: 启动 Explore subagent "搜索登录相关代码"
```

**问题:**
- 对于已知问题位置的情况,使用 subagent 是过度设计
- 浪费时间和 token
- subagent 可能找不到错误日志已经指明的问题

### ✅ 推荐的做法

**情况 A: 如果知道具体位置**

```
用户: "登录时出现 500 错误,错误日志指向 src/auth/controllers/auth.controller.ts:45"

助手: 直接使用 Read 工具读取文件
然后使用 Grep 搜索相关的错误处理代码
```

**情况 B: 如果不清楚问题位置**

```
用户: "登录时出现 500 错误,不知道具体位置"

助手: 使用 debugging-toolkit:debugger subagent
"诊断登录功能为什么返回 500 错误。检查 auth.controller.ts、
相关的服务层和数据库操作。识别错误原因并提供修复建议。"
```

**优势:**
- 针对已知位置 → 直接处理效率高
- 未知问题位置 → 专业的调试 subagent 更有效
- 避免不必要的 subagent 开销

## 场景 3: 重构大型功能

### ❌ 不推荐的做法

```
用户: "重构整个认证系统,从 Session 改为 JWT"

助手: 直接开始修改代码,逐个文件编辑
```

**问题:**
- 可能遗漏关键的依赖关系
- 无法全面理解重构影响范围
- 可能引入新的 bug
- 缺乏系统性的重构方案

### ✅ 推荐的做法

```
用户: "重构整个认证系统,从 Session 改为 JWT"

助手 1: 使用 Plan subagent
"规划将认证系统从 Session 迁移到 JWT 的方案。分析现有实现,
识别需要修改的组件,制定分步骤的重构计划。"

助手 2: 使用 Explore subagent (very thorough)
"全面分析当前 Session 认证系统的所有使用位置,包括:
- 中间件和拦截器
- 控制器和路由
- 数据模型和存储
- 配置和环境变量
返回完整的依赖关系图。"

助手 3: 使用 general-purpose subagent
"按照重构计划执行以下步骤:
1. 安装 JWT 相关依赖
2. 创建 JWT Token 服务
3. 实现新的认证中间件
4. 更新所有控制器
5. 移除 Session 相关代码
6. 更新测试用例"

助手 4: 使用 code-reviewer subagent
"审查重构后的认证系统代码,检查:
- 安全性 (Token 加密、过期时间)
- 性能 (Token 验证效率)
- 错误处理
- 最佳实践
提供改进建议。"
```

**优势:**
- 系统化的重构方法
- 全面理解影响范围
- 避免遗漏关键组件
- 专业的代码审查确保质量

## 场景 4: 读取配置文件

### ❌ 不推荐的做法

```
用户: "读取 config.yaml 文件"

助手: 使用 Explore subagent "找到并读取配置文件"
```

**问题:**
- 对于明确的文件读取,使用 subagent 是过度设计
- 增加了不必要的复杂度
- 浪费时间和 token

### ✅ 推荐的做法

```
用户: "读取 config.yaml 文件"

助手: 直接使用 Read 工具读取文件
Read(file_path="config.yaml")
```

**优势:**
- 直接、快速、高效
- 无需启动额外的进程
- 节省 token

**预期输出:**
```
server:
  port: 3000
  host: localhost

database:
  host: db.example.com
  port: 5432
  name: myapp
  ...
```

- 快速、精确
- 直接返回结果

## 场景 6: 查找所有性能问题

### ❌ 不推荐的做法

```
用户: "找到项目中所有可能存在性能问题的地方"

助手: 使用 Grep 工具逐个搜索 "slow", "performance", "optimize" 等关键词
```

**问题:**
- 性能问题不一定会用特定关键词标注
- 需要理解代码逻辑才能判断
- 可能遗漏没有明确标注的问题
- 多轮搜索效率低

### ✅ 推荐的做法

```
用户: "找到项目中所有可能存在性能问题的地方"

助手: 使用 code-reviewer subagent
"全面审查项目代码,识别潜在的性能问题,重点关注:
1. 数据库查询 (N+1 查询、缺少索引)
2. 循环和递归 (复杂度过高)
3. 缓存策略 (缺少缓存、缓存失效)
4. 并发处理 (锁竞争、死锁)
5. 内存使用 (内存泄漏、大对象)
返回具体的问题位置、严重程度和优化建议。"
```

**优势:**
- 专业的性能分析
- 全面的代码审查
- 具体的优化建议
- 按严重程度排序

**预期输出:**
```
发现以下性能问题:

🔴 严重:
1. src/user/user.service.ts:145 - N+1 查询问题
   在获取用户列表时,为每个用户单独查询角色信息
   建议: 使用 JOIN 或批量查询

2. src/cache/redis.service.ts:89 - 缓存穿透
   缺少对不存在数据的处理
   建议: 实现布隆过滤器或空值缓存

🟡 中等:
3. src/export/export.service.ts:234 - 大内存对象
   在内存中加载整个数据集
   建议: 使用流式处理或分页

4. src/api/middleware/rate-limit.ts:56 - 锁竞争
   多线程环境下的性能瓶颈
   建议: 使用读写锁或无锁算法

🟢 轻微:
5. src/utils/date.ts:12 - 重复计算
   日期格式化在循环中重复执行
   建议: 提取到循环外部
```

- 无法理解模块之间的关系
- 缺乏架构层面的分析
- 返回的信息杂乱无章

- 系统性的架构分析

## 决策流程示例

### 示例 1: 用户请求探索代码库

```
用户: "这个项目是如何处理支付的?"

决策过程:
1. 是否需要理解代码库? → 是
2. 是否需要探索性分析? → 是 (不确定支付代码的位置)
3. 决策: 使用 Explore subagent (medium thoroughness)

执行: Explore subagent 找到支付相关的所有代码,
包括支付处理、验证、回调等组件。
```

### 示例 2: 用户请求简单操作

```
用户: "把 config.json 中的端口从 3000 改为 8080"

决策过程:
1. 是否需要理解代码库? → 否 (已知文件位置)
2. 工具调用次数? → 1 次 (Read + Edit = 2 次简单操作)
3. 目标是否明确? → 是
4. 决策: 直接使用 Read 和 Edit 工具

执行: Read 工具读取文件 → Edit 工具修改端口
```

### 示例 3: 用户请求复杂重构

```
用户: "重构 API 路由,使用 RESTful 规范"

决策过程:
1. 是否需要理解代码库? → 是 (需要分析现有路由)
2. 工具调用次数? → 5+ 次 (分析、设计、实现、测试)
3. 是否需要规划? → 是 (需要设计新的路由结构)
4. 决策: 组合使用 Plan + Explore + general-purpose

执行:
1. Plan subagent 设计 RESTful 路由方案
2. Explore subagent 分析现有路由
3. general-purpose subagent 执行重构
4. code-reviewer subagent 审查结果
```

## 场景分析说明

### 为什么有些场景需要 Subagent?

**1. 需要理解代码库结构**
- 单个工具调用无法获取足够的上下文
- 需要多轮搜索和分析
- 需要综合多个来源的信息

**2. 需要复杂分析**
- 需要专业知识 (性能、安全、架构)
- 需要深度分析代码逻辑
- 需要识别潜在问题

**3. 需要多步骤操作**
- 需要动态调整执行计划
- 需要处理执行过程中的问题
- 需要保持上下文的连贯性

### 为什么有些场景不需要 Subagent?

**1. 简单单步操作**
- 读取单个文件
- 简单文本编辑
- 明确的文件查找

**2. 精确的搜索目标**
- 已知确切的类名或函数名
- 搜索目标具体且单一
- 无需理解上下文

**3. 避免不必要的开销**
- Subagent 会增加额外的 token 消耗
- 简单任务直接处理更高效
- 避免过度设计

## 实战建议

### 快速决策法 (3 秒法则)

问自己: **"我能在 3 秒内判断出需要哪个工具/文件吗?"**

- **是** → 直接使用工具
- **否** → 使用 subagent

### 复杂度评估法

评估任务的复杂度维度:

1. **文件数量** - 涉及多少个文件?
2. **分析深度** - 需要多深的理解?
3. **执行步骤** - 需要多少个步骤?
4. **专业知识** - 需要专业知识吗?

**总分 < 5** → 直接处理
**总分 ≥ 5** → 使用 subagent

### 试错法

如果不确定:

1. **先尝试直接使用工具**
2. **如果发现需要多次搜索或分析** → 切换到 subagent
3. **记录经验,优化判断**

---

## 总结

**核心原则:**
- Subagent 为复杂任务设计,简单任务直接处理
- 理解每个场景的特点和需求
- 基于任务性质选择最合适的方法
- 避免过度使用或不当使用 subagent

**记住:**
- [ ] 探索和理解 → Subagent
- [ ] 简单操作 → 直接工具
- [ ] 专业分析 → 专业 Subagent
- [ ] 多步骤任务 → general-purpose
- [ ] 单文件操作 → 不使用 Subagent
- [ ] 明确搜索 → 不使用 Subagent
